# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

musdash is a Coolify-style self-hosted PaaS written in Go, designed around one constraint: the control plane and proxy together idle under 50 MB RAM (server under 30 MB, proxy under 20 MB). It ships as one static binary with no Node, Postgres, Redis or separate proxy product.

Two documents drive the work; read them before designing anything:

- `docs/spec.md` — the full product spec: architecture, feature list by phase (0–9), data model, RAM rules, security checklist. It still uses the working name `litepaas`; the real name is `musdash` everywhere (binary, module, data dir, `MUSDASH_*` env vars).
- `docs/plans/phase-N-*.md` — the implementation plan for each phase, with task checklists, the file map, and a table of decisions that override or extend the spec. Where plan and spec disagree, the plan wins.

The build proceeds phase by phase, task by task. `git log` and the plan's task list show where it stands; packages named in the spec's layout (`auth`, `docker`, `deploy`, `proxy`, …) do not exist until their phase.

## Commands

```sh
go vet ./... && go test -short ./...                   # required green before every commit
go test ./internal/jobs -run TestLockKeySerialises -v  # one test

make generate     # templ → *_templ.go, and input.css → static/app.css (run after editing either)
make build        # release build into bin/musdash
make build-linux  # dist/musdash-linux-{amd64,arm64}
make dev          # server against ./data with the component gallery at /_ui
make rss          # idle-memory test on this machine
make rss-linux    # the same test in a Linux container: the authoritative figure
make catalog-test # vet and test tools/catalog, a module of its own that ./... does not reach
```

- `bin/` is git-ignored. `bin/tailwindcss` is the Tailwind v4 standalone CLI, downloaded by `make tools`; there is no Node toolchain.
- Generated files (`*_templ.go`, `internal/web/static/app.css`) are committed so a plain `go build` needs only Go. Regenerate both after editing any `.templ` file, `input.css`, or class names in `app.js`. `internal/web/static` embeds `app.css` by name, so the package does not compile until that file exists.
- Subcommand flags fall back to env vars: `--data` / `MUSDASH_DATA`, `--dev` / `MUSDASH_DEV=1`. `MUSDASH_MASTER_KEY` (base64, 32 bytes) overrides `<data>/master.key`.

## Hard constraints

These come from the spec and shape every change:

- **Three external modules only**: `modernc.org/sqlite`, `golang.org/x/crypto`, `github.com/a-h/templ`. Everything else is the standard library (`net/http` mux, `log/slog`, `flag`, `embed`). Spec section 3 lists what is deliberately avoided (routers, Docker SDK, YAML, JWT, cron and session libraries). Do not add a dependency without the user's say.
- **Shell out, don't import SDKs**: `docker`, `docker compose` and `git` are run as processes with `--format json` where output is parsed.
- **RAM rules (spec section 8)**: stream with `io.Copy`, never buffer command output, logs or uploads; no in-memory caches of database rows; no goroutine per container; small fixed worker pool; bcrypt, not argon2; `CGO_ENABLED=0`.
- **Injection safety**: local commands are argument vectors, never shell strings. Anything that reaches a shell (SSH) goes through `runner.Quote` / `runner.QuoteJoin`. User values passed as arguments are guarded with `--` against option injection.
- **Secrets at rest** are AES-256-GCM sealed with the master key (`secret.Box`). Session and API tokens are stored only as SHA-256 hashes (`secret.HashToken`).

## Architecture

One binary, two long-running processes: `musdash server` (UI, API, webhooks, jobs, SQLite) and `musdash proxy` (edge reverse proxy with autocert). They are separate so restarting the control plane never drops app traffic; the server rewrites `<data>/proxy/routes.json` atomically and signals the proxy with `SIGHUP`. Containers publish to a loopback port musdash assigns (20000–29999) and the proxy routes `Host` to that port; containers of one environment also share a Docker network and reach each other by app name. Remote servers are agentless, driven over SSH.

How the existing packages fit together:

- `cmd/musdash` — subcommand dispatch with plain `flag` sets. `commonFlags` registers the shared flags; `openDB` creates the data directory tree and returns a migrated database.
- `internal/config` — owns the data directory layout (every path under `DataDir` is a method here; add new paths here rather than joining strings elsewhere) and loads or creates the master key, refusing a key file readable by group or others.
- `internal/auth` — password hashing and rules, the `Limiter` every attempt counter uses (bounded at 4096 keys), and TOTP (`totp.go`: RFC 6238, checked against the RFC's vectors). `TOTPCheck` takes the last accepted step and accepts only a later one; the caller stores the step with `db.UseTOTPStep`, which is one statement, so a code works once even for two requests at the same moment.
- `internal/secret` — `Box` (seal/open) plus all random generation. `RandomID()` is the id for every row: 12 chars of `[a-z2-7]` starting with a letter, safe as a URL segment, container name and DNS label. Named `secret`, not `crypto`, to avoid shadowing the stdlib.
- `internal/db` — `Open` sets the pragmas the RAM budget depends on (WAL, 2 MB cache, 2 connections, `_txlock=immediate` so two connections cannot deadlock on a write upgrade). `Migrate` applies numbered files from the `migrations` package once each, in a transaction. Queries are hand-written methods on `*DB`, one file per area.
  - Every query for a team-owned row takes `teamID` and filters on it; a miss returns `db.ErrNotFound` whether the row is absent or belongs to another team, so handlers answer 404 either way.
  - Writes go through the `affected(...)` helper to turn zero rows into `ErrNotFound`; multi-statement writes use `d.Tx`.
  - Tables are `STRICT`, timestamps are Unix seconds in `INTEGER`, text columns default to `''` rather than NULL.
  - An install has one team, and an account is a member of it: `RemoveMember` deletes the account with what hangs from it. `keepsAnOwner` runs inside the transaction of every change that could leave the team without an Owner.
  - Authority is not held on to past the role it came from. Raising a role ends that person's sessions, reset links and API tokens (`SetRole`): a reset link made for a Member must not be one for the Owner they become. Lowering a role, or removing the member, withdraws the invitations they made, and `AcceptInvitation` asks again whether the maker may give that role. What one member does to another (`RemoveMemberBy`, `CreatePasswordResetBy`, `DisableTOTPBy`) is checked by `managing` inside the transaction that acts, not only when the page was drawn. A password change or reset and turning the second step on end the person's API tokens with their sessions. A new way to act on an account, or a new long-lived credential, has to fit these.
  - A tag is a row of `tags` (`team_id`, `tag`), which can exist with nothing tagged; `resource_tags` says what has it. `SetTags` makes the tags it is given that the team does not have, up to `MaxTeamTags`; `RenameTag` and `DeleteTag` change both tables in one transaction.
  - `shared_vars` and `resource_tags` carry `team_id` themselves, and every query on them filters on it besides the scope or resource id: a row that named another team's project, server or app must find nothing. `shared_vars` rows go with their project, environment or server by trigger (the cascade from a project to its environments is the database's own).
  - `Search` (`search.go`) is what the search in the bar asks: one statement, a `UNION ALL` over what a team has that has a page (projects, environments, apps, databases, services, domains, servers, tags), the team's id in every arm, ranked and cut in the database. Nothing of it is kept between requests. What was typed reaches the statement as parameters only, escaped for `LIKE`. A new arm filters on the team itself, leaves previews out, and puts no sealed column and no variable into `own`: a search that matched inside a secret would say what it holds.
  - `TokenByHash` joins the membership: an API token is live only while its person is in the team, and it carries the role they hold now.
- `migrations/` — a tiny Go package exposing an `embed.FS` of `NNNN_name.sql` files (`go:embed` cannot reach parent directories). Add a new numbered file; never edit an applied one.
- Paths: `config.Config` describes the control plane's data directory. A path handed to a Runner must come from `deploy.PathsOn(cfg, r)` (in the deployer, `d.at(r)`), which is the same layout under the data directory of the server that Runner reaches; on this machine the two are the same. Logs that the control plane writes itself (`DeployLogPath`, `ServiceLogPath`, `TaskLogPath`) come from the plain `Cfg`.
- `internal/runner` — the `Runner` interface is the only way any package touches a server: commands (`Run` streams, `Output` is capped at 1 MiB and errors rather than truncating) and file operations (`WriteFile` is atomic; over SSH the file gets its name in a second command, sent only when everything was read and written, because to the command that writes, a connection that dropped looks like the end of the file). `LocalRunner` uses `os/exec` with its own process group so cancelling a context also kills children. `SSHRunner` runs each command as a session on one connection, quoting every value with `Quote`; a command's environment travels in a `0600` file the remote shell sources and removes, never on the command line; a cancelled context kills the remote command; `Dial` opens a connection from the server's side (health checks use it). Opening a session and starting a command end with the caller's context, a keepalive closes a connection whose server stopped answering, and a connection carries eight sessions before another is opened (sshd refuses the eleventh). `runner/sshtest` is an SSH server for tests that runs commands with the local shell, so remote paths are tested against the real protocol. Code written against `Runner` must not assume it is local.
- `internal/jobs` — a persistent queue on the `jobs` table. One dispatcher goroutine claims work with a single `UPDATE … RETURNING` and runs up to N handlers. Jobs sharing a `lock_key` never overlap (this is how "one build per server" is enforced). Errors retry with back-off; wrap with `jobs.Permanent` to fail at once. Jobs left `running` by a crash are requeued in `Start`; a job interrupted by shutdown is requeued without spending an attempt.
- `internal/servers` — `Pool.Runner(server)` is where every package gets its Runner; only this package knows whether a server is local or SSH. A remote server has one pooled SSH connection, opened by the first command and closed after five idle minutes; the Runner handed out holds none itself and borrows it per call. `Check` makes the first contact, which is the only place a host key is recorded; everything else refuses a server without one. So what must be true of a server before anything else may reach it is looked at in that contact, before the key is recorded (`firstContact`'s `look`): a data directory that holds somebody else's things leaves the server unchecked, because the first connection of a process empties `<data>/work`. Whose a directory is, is told by the file a check leaves in it (`ownedMark`), not by names such as `apps`; the sweep asks the same question (`oursFunc`) before it removes anything. A first contact asks for the Ed25519 host key, then ECDSA, then RSA (the library's own order has ECDSA first, and people are told to compare the Ed25519 one); a recorded key is asked for by its kind and no other. `InstallProxy` copies the binary and writes the systemd unit.
  - A remote server is not trusted with the control plane: what it answers (its architecture, versions, file listings) is data. Before any of it becomes part of a path or a command here, it is checked against a known set or a strict pattern, and before it is stored it is cut to size. Nor is it trusted with the other servers: status updates from `docker events` match the reporting server's id, and an image moved from a build server goes through `docker.FilterSaved`, which lets it carry the built image's name and no other.
  - A server that hangs must hold up only its own commands. Nothing waits on a remote answer while holding a lock that other servers need (the routes lock is per server; the pool asks `Alive` outside its locks).
  - `Terminal` runs a command on a terminal of its own, for a person to type into: locally on a pseudo-terminal opened with the `syscall` package (`pty_linux.go`, `pty_darwin.go`; ioctls go through `SyscallConn`, because `File.Fd` would make reads uninterruptible), over SSH in a session that asked for one. Closing it hangs up what was running.
- `internal/docker` — builds argument vectors for the docker CLI. `RunSpec.Args()` validates every value (image names against the reference grammar, mounts, labels) so nothing a person typed can be read as a flag. Bind-mount sources go through `CheckBindSource`, which refuses the Docker socket, system directories and the musdash data directory.
- `internal/deploy` — the deploy job (`pipeline.go`): pull → network → env file → start on a fixed loopback port → health check → `SyncRoutes` → stop the old container. A failure before the switch removes the new container and leaves the old one serving; when it was the process that died, `Reconcile` removes that container at the next start (a failed deployment's container is never protected, `db.ProtectedDeployments`). An environment's network is removed from a server with the environment's last app, database or service there (`dropNetwork`): the records decide, not the containers, so a network is never taken from under something stopped or being deployed. `monitor.go` holds one `docker events` stream per server and updates app status through `db.SetAppStatusIf`, which ignores containers that are not the app's serving one. `routes.go` regenerates a server's whole `routes.json` from the database and signals the proxy.
  - Every deployment's image stays on the server under a name of that deployment's own (`musdash/<app>:d-<deployment>`, in `deployments.kept_image`; a built image also has its commit's tag, which moves when the commit is built again), the newest five by deployment. App containers are started with `--pull never`. `Rollback` queues a deployment that runs such a name again and pulls or builds nothing. The name must be in the app's own repository (`ownImage`), checked when queued and again when run: a deployment row must never decide what another app's image is.
  - Health-check URLs are built by `HealthURL` with a fixed loopback host; never concatenate a user path onto a URL.
  - Unit tests script the server with `runner/runnertest.Fake` to inject failures; `test/deploy_test.go` runs the same flow against real Docker when `MUSDASH_DOCKER_TEST=1`.
  - `build.go` is the Git path: clone → `git ls-tree` symlink check → `docker build`. Credentials reach git and docker through their environment (`GIT_CONFIG_*`, `GIT_SSH_COMMAND`, `--build-arg NAME`), never an argument or URL. Clone and build are bounded by `cloneTimeout` / `buildTimeout`. `options.go` is the allow-list for a person's extra `docker run` options: add a flag only if it can neither reach the host nor loosen a limit musdash sets.
  - `builders.go`: Nixpacks and Railpack. A builder is never installed on a server: it runs in a container made from an image built on first use (`ADD --checksum` of a pinned release), with no socket, no capabilities and a read-only root, and it only plans; `docker build` builds. A variable that a plan names and the app does not have comes from the repository, so it is passed as `--build-arg NAME=value` (`BuildSpec.PlainArgs`), never through the docker command's environment, which is where the app's own build variables travel by name. A builder sees the checkout read-only; Nixpacks, which must leave `.nixpacks/Dockerfile` next to the app, gets that one directory to write to, and the server is asked that what it left is not a link before it is read. A builder's container has a name and is removed by it after a run that failed. Images under `musdash/` are musdash's own (apps' builds, the builders): `compose.Validate` refuses a stack that names one.
  - `preview.go`: a preview is the deployment of a pull request, an app of its own whose `preview_of` is the app it belongs to. `SyncPreview` creates it and queues a deployment of the pull request's branch (each deployment first takes the parent's settings again, `db.RefreshPreview`); `ClosePreview` queues its removal under its own deployment lock. `wantsPreview` is the gate, and its one rule that must never loosen is that the pull request's branch is in the app's own repository: a fork's code is not built or run with the app's variables. A preview has no variables, files or settings of its own (`App.ConfigOwner` is its parent); it is listed with its parent and by no other query (`ListApps` and `AppsForPush` leave previews out).
  - `shared.go`: a value names a shared variable as `{{team.NAME}}`, `{{project.NAME}}`, `{{environment.NAME}}` or `{{server.NAME}}`. `expandShared` fills them in where variables are written for a deployment (an app's env file and build arguments, a service's variables file), from the resource's own team, project, environment and server (`db.ScopeOf`, `db.SharedFor`). What is stored keeps the name. Only that exact form is read (a backslash before it keeps the text for the app itself), what is put in is not read again (no nesting, no loop), and a name that does not exist fails the deployment with the name, never with a value. Nothing is handed to a container that did not name it: do not add inheritance.
  - `database.go` is a database's whole lifecycle. One container per database (`musdash-db-<id>`), replaced in place: stop the old one, then start the new one on the same volume, never two at once. The password reaches the container only through a `0600` env file; engines without a password variable read it from their own environment in a `sh -c` command. Start is a job (`JobDatabase`, lock key `database:<id>`); stop and destroy run in the request under the same per-id lock as apps.
- `internal/catalog` — what musdash can run out of the box: the database engine templates and the service templates (`services/*.yaml`, Compose files with a `# key: value` header: `name`, `about`, `docs`, `website`, `categories`, `source`, `connect`). `magic.go` is the `SERVICE_*` variable convention shared with Coolify's templates: address variables get their value from an endpoint's domain, the others are generated once and stored sealed. A template is data (image, env, command, health command, URL format); adding an engine should not need code elsewhere. `TestEveryEngineStartsWithDocker` is what proves a template against its real image.
  - The service catalogue is several hundred templates. Six were written for musdash (`ownTemplates` in the test: no `source` line, started for real by `TestCatalogueWithDocker`); the rest are Coolify's and Dokploy's, made by `tools/catalog`, a Go module of its own with a YAML parser that is no part of the binary. Do not edit an imported template by hand: change the converter (or `overrides.go`, `rejected.txt`) and run it again. A template's logo is the converter's too (`tools/catalog/logos.go`): where it looks and in which order is `logoPlaces`, the three lists written by hand are `logoAlias` (a product under another name), `logoPicked` (one file from a collection of every kind of brand) and `logoForDark`, and a drawing in white for a dark page is not taken as it is (`unseen`). A logo is at most 6 KB wherever a service has a file that small, and at most 20 KB where it has none (`smallLogo`, `maxLogo`): do not make one limit of the two, or the larger file that comes earlier in the order replaces the small one. A service with no drawing gets a picture (`pictures.go`): headless Chrome, started by the converter, draws the file on a page served from this machine and sends back a WebP; a file is only ever an `<img>` to it. A logo drawn in white is put on a dark square (`onDark`, and in the picture's page), and `logoForDark` names the ones no rule sees. `CATALOG_NOTES=1` says why a file it found was refused. `docs/plans/service-catalogue.md` has the rules of the conversion; `services.LICENSE` and `services.SOURCES` say whose each template is; `docs/catalogue-left-out.md` lists what could not be converted and why. An imported template publishes a port only for what the proxy cannot carry (`tools/catalog/ports.go`): the ones its source named, moved out of musdash's loopback range, and never one `deploy.ValidPublicPort` refuses (`TestCatalogueTemplatesPublishPortsAStackMay`). The six written for musdash publish none.
  - `Services()` is what the headers say and holds no Compose text; `Service(key)` reads the one file, and `ServiceName(key)` is for a page that only names a template. Do not put the text back into the list: it is what the Add resource page walks.
  - A template names one to three of `catalog.Categories`, a fixed list. A new category is a line there; the page's Category menu (`ui.MultiSelect`, `data-filter-pick`) lists the ones in use, and the database engines are found under `database`.
  - A service from a Git repository (`db.TemplateGit`) goes through the same steps with three differences: the Compose text comes from a fresh clone, the sandbox gets the checkout mounted read-only (so `include` and friends can read the repository and nothing else), and `build:` is allowed inside it. Each deployment clones into a checkout directory of its own (`src-<id>`), because the running stack may have files of its checkout mounted; the others are removed once a stack is up from the new one. Those mounts are forced read-only and every checkout path the stack reads is validated (`source.ValidRelPath`) and checked with `git ls-tree` for symlinks (git runs with `GIT_LITERAL_PATHSPECS`, or a name starting with `:` would be answered for another file): a writable or linked path would let one container redirect another's mount out of the checkout.
  - `service.go` deploys a Compose stack: variables file → sandboxed load twice (once raw, to see where variables are used; once filled in) → `Validate` → host ports for endpoints → `Apply` → `compose.resolved.json` (0600) → `docker compose pull` and `up --wait` against that file only. The person's own text is never given to Compose on the server.
- `internal/compose` — Compose without a YAML parser. `Config` runs `docker compose config --format json` in a container with no network, no mounts and no socket (the file on stdin), because loading a Compose file reads other files (`include`, `extends`, `env_file`) and on the server those could be any file musdash can read. `Validate` is an allow-list over the normalised JSON: a key it does not know is refused, since Compose keeps adding keys and some act on the host. When allowing a new key, ask what its *values* can reach. `Apply` adds only what musdash needs (labels, loopback ports, restart policy, the environment network).
- `internal/ops` — what musdash does on its own. `Run` ticks once a minute: schedules that are due are claimed in one `UPDATE … RETURNING` (their `next_run` becomes `-1` until the real next time is stored), and a job is queued for each. The jobs: backup (dump → optional upload → retention), restore, scheduled task (`docker exec` in the app's serving container), daily Docker clean-up. Backup, restore and a database's start share the lock key `database:<id>`.
  - A backup or run row is created `running` when it is queued. `Recover` (before the queue starts) fails the ones a dead process left, and each job returns at once when its row is no longer `running`: that is what makes a requeued job harmless.
  - `Notify` only queues an event; one goroutine delivers. Producers set `Event.URL` to a dashboard path and `deliver` makes it absolute. `deploy` reports through the `Deployer.Notify` hook so it does not import this package.
- `internal/backup` — `Dump` and `Restore` stream between `docker exec` and a gzip file through the Runner; `S3` runs `rclone` in a container on demand with the keys in an env file that is removed afterwards.
- `internal/cron` — the five-field parser and `Next`, in UTC.
- `internal/notify` — one function per channel kind over `net/http` and `net/smtp`. `Dialer` refuses loopback, link-local and unspecified addresses at connection time, so a redirect or a DNS answer cannot get around the check.
- `internal/metrics` — what a server (`/proc`, `df`) and its containers (`docker stats`) use, asked only when a page or the sampler wants it. An answer is the server's word: every value is parsed into a number or dropped, and nothing of it is kept as text but a container's name that looks like one. `ops/metrics.go` samples the servers that sampling is on for, each in a goroutine of its own with a time limit, into `metric_samples`, which keeps a day.
- `internal/source` — everything about a Git host that is not a process: `ParseRepo` / `ValidBranch` / `ValidRelPath` (the only validators for values that reach git), the GitHub App client, the GitLab client (`gitlab.go`), `ReadHook` (streaming check of the secret plus the few values a push or a pull request event needs; which of the two a body is, and which host sent it, is read from the body, since the headers that say so are not signed: GitHub's, GitLab's and Bitbucket's shapes are all looked for in the one pass, and every way a host proves the secret (`Proof`) is tried against the one secret), deploy-key generation.
  - A source (`git_sources`) is a GitHub App or a GitLab access token with its instance's address (`db.GitSourceGitHubApp`, `db.GitSourceGitLab`). A source id therefore says nothing about the host: ask the row's `Kind`. A GitHub App is unfinished until GitHub has returned its credentials, and only such rows are pending, listed out or cleaned up (`gitSourceReady`); a GitLab row is whole when made. Only a GitHub App reports pushes (`GitSource.ReportsPushes`): what deploys through a GitLab source uses the app's own webhook, and nothing is written on a merge request.
  - `source.GitLab` connects to an address a person typed, so its client dials only where `netguard.Policy` allows, sends the token as a Bearer header and follows no redirect. What an instance answers is data: a user name and a project path are checked against a pattern before they are kept. A source's credentials go to its own host and nowhere else: the Git form checks the repository's host (`sourceHost`), and the clone checks it again (`cloneAccess`, `gitLabAccess`).
- `internal/proxy` — `Table` is an immutable, validated route set swapped atomically; targets must be loopback. Port 80 serves ACME challenges, redirects TLS hosts and proxies HTTP-only ones. Certificates are requested only for routed hosts with `tls: true`. `certs.go` stands between a handshake and autocert, which would order a certificate inside the handshake for up to five minutes and tell nobody when it failed: a handshake waits until eight seconds after its connection arrived (less than the server's own deadline for one, so the visitor gets a TLS error), one caller a host and kind of key is inside the manager at a time, and that caller logs what came of it, for routed hosts only.
  - A host can have several routes, by path prefix: the longest that matches on a segment boundary serves. On a host where the path decides, or where a route has a password, a request whose path is not in its simplest form is redirected to that form before anything is matched, so the proxy and the app never read a path differently.
  - A route's password is a bcrypt hash in `routes.json` (hence `0600`). `gate` checks it: verified credentials are remembered for five minutes after their last use under an HMAC that includes the route's hash, one comparison runs at a time, and each route has only a few places in the line for it.
  - The proxy reads a path more strictly than some apps do. `Table.Guard` closes the gap for a host that is open at one path and guarded at a longer one: a request whose path, read loosely, falls under the guarded route asks for its password.
  - `routes.json` is read by whatever proxy is running, which after an upgrade can be an older one. A field an older proxy would ignore to dangerous effect (a path, a password) therefore puts the whole host under a key it does not read (`routes_v2`, `Route.NeedsV2`): unknown to it, not open. Do the same for the next such field.
  - A host is shared by path only among one team's resources on one server (`db.AddDomain`), and the dashboard's own domain gives no path away: a page under it would have the dashboard's origin.
- `internal/web` — templ + HTMX (SSE extension) with assets embedded in the binary; no JSON API for the UI.
  - `static/` serves embedded assets at `/static/{name}?v=<content hash>` with immutable caching and lazy gzip. Use `static.URL(name)` in templates; a new asset must be added to the `go:embed` line. A `logo-*` file is the exception to the caching in memory: there are several hundred, so one is hashed and answered from the embedded file and never kept on the heap or gzipped (`TestALogoIsNotKept`). A logo is a drawing (`logo-<name>.svg`) or, for a service that has none the dashboard can show, a WebP picture of at most 96px and 6 KB (`logo-<name>.webp`); `static.Logo(name)` says which a name has, and it has one of the two.
  - `static/app.js` is driven entirely by `data-*` attributes (`data-open`, `data-close`, `data-match`, `data-confirm`, `data-autoopen`, `data-filter`, `data-filter-pick`, `data-filter-clear`, `data-filter-count`, `data-copy`, `data-autodismiss`, `data-follow`, `data-nav-toggle`, `data-select`, `data-select-multi`, `data-alone`, `data-address`, `data-menu-end`, `data-menu-actions`, `data-search-open`, `data-search-field`) so pages carry no inline script and the CSP can forbid it.
  - There is no native `<select>` in the UI: `ui.Select` is a button, a popover list (the browser's Popover API, so nothing clips it and Escape or a click elsewhere closes it) and a hidden input with the value. `app.js` places the list by its button through the CSSOM, which the CSP allows; a `style` attribute it does not. `ui.Combobox` is the same with a filter field in the menu, which a `Select` of more than eight options gets on its own. `ui.Picker` is a filtered menu that fills another field and fetches its options (`ui.PickerOption`) when first opened, for a list that is slow or long: the repository picker is one. `ui.MultiSelect` is the choice of several: its options are real checkboxes under their labels (so a form sends each under the one name and the browser keeps them with the page), choosing leaves the menu open, and the button counts what is chosen. With `data-filter-pick` it narrows a list to the items that have any of the chosen values, beside a `data-filter` field; a `data-filter-clear` button undoes both and is there only while there is something to undo.
  - A menu of things to do or places to go is `ui.Menu` with `ui.MenuItem`s (the person's menu in the bar is one). It is not a `Select`: nothing in it is the chosen one, so it opens with nothing marked and the focus on its button (`data-menu-actions`), and the arrow keys go into it. An item is a link (`Href`), a button that opens a dialog (`Opens`) or, with neither, the submit button of the form it is in. `MenuItem.Danger` is for what ends or removes something: red text, a pale red under the pointer, and its question (`ui.Ask`) asks with the danger button. `Current` marks the page the person is on.
  - What opens over the page has the page out of reach, as a `<dialog>` has. A press outside an open list (everything in a `[data-select]`: a Select, a Menu, a switcher) closes it and is spent on that: `app.js` keeps that press's `mousedown` and `click` from the page, and the stylesheet takes the pointer from the page while a `.menu` is open, so nothing behind lights up. Below 64rem the sidebar is a drawer: the element after it is its backdrop (`.sidebar-backdrop`, the dialog's own dim, `--color-backdrop`), the page (`.main`) is `inert` while it is open, the focus goes in and comes back to the bar's button, and it has a Close button of its own, since the bar's is behind the backdrop.
  - The search (`ui/search.templ`, `handlers_search.go`, `pages/search.templ`, `docs/plans/search.md`) is a button at the end of the bar, before the person's menu, and one `<dialog>` in every page that holds no results: its field asks `GET /search?q=` as it is typed in and the answer, rows that are links, becomes its list. It opens on `/` outside a field and on Cmd+K (Ctrl+K off a Mac, where Ctrl+K belongs to text fields), and never over another dialog. Rows are `db.Search`'s hits and the pages of `ui.Destinations`, which is the sidebar's own list for the person's role and their account, so the search offers no page the sidebar does not; with nothing typed it lists those pages. The answer is 200 whatever happened, as a switcher's is. `app.js` keeps Enter from opening a row of the search before: while the list is older than the text, Enter waits for the answer. A thing with a page that should be found gets an arm in `db.Search` and a case in `pages.HitRow`.
  - `ui/` holds the reusable design-system components (props structs + templ); `pages/` holds pages built from them.
  - Where a page is, is in the bar at the top (`ui.Trail`, from the crumbs a handler gives `s.shell`): build them with `projectCrumbs`, `envCrumbs` and `resourceCrumb` (`handlers_resources.go`). The bar has no box of the page's width inside it: it starts with the trail and ends with the person. The layout puts the team in front of every trail (`ui.trail`, from `Shell.Team`, which is the session's `TeamName`), so a handler never names it; it is a switcher (`/switch/teams`) that lists the one team an install has. The person's menu at the end (`userMenu`) holds what is theirs: the account, Settings for an Admin, and Sign out, which is the one logout form and where tests read the CSRF token from. The sidebar is navigation only. A crumb with a `Menu` is a switcher, whose options are fetched when it is first opened: the project's step lists the team's projects (`projectCrumb`, `/switch/projects`), a tag's the team's tags (`/switch/tags`), the environment's and the resource's what is beside them (`/projects/{id}/switch/environments`, `…/env/{env}/switch/resources`); those answer 200 with a note when they cannot list, because htmx swaps nothing else in.
  - Where something is, is in its address: the project, then the environment, then the kind and the resource, `/projects/{project}/env/{env}/app/{id}/…` (`database`, `service`: the kind is `db.KindApp` and the others, so the path is built from it). Build one with `pages.EnvPath`, `pages.ResourcePath` or a view's `Path()`, never from strings: a fragment that has only the row is given its base (`placeInPath`). Everything of an environment is under `inEnv` (`place.go`), where `{id}` is still the resource and `loadProjectEnv` reads `{project}` and `{env}`, which does not find an environment of another project. A resource's route is registered with `app(…)`, `database(…)` or `service(…)` in `server.go`, which put `s.placed` in front of the handler: the three ids have to belong together (`db.PlaceOf`), or the answer is 404, so a page has one address and no handler has to ask. `/projects/{id}` is the project's own page, with no environment in it. `/apps/{id}/…`, `/databases/{id}/…` and `/services/{id}/…` are the short address, for `GET` only: they lead to the long one with the rest of the path and the query (`s.short`). What musdash sends outside is written short (a notification's `Event.URL`): it needs no lookup when it is made, and every message already sent holds one. Nothing inside the dashboard links to a short address, and no form posts to one. A list that crosses projects carries where each thing is (`db.Places`, `Hit.ProjectID`, `Event.EnvironmentID`).
  - A project has two tabs (`projectTabs`). **Environments** is its page (`/projects/{id}`, `pages.ProjectShow`), where an environment is chosen: the project's environments as tiles, each with the counts of what is in it (`db.ListEnvironments`), and **Add environment** in the header, a dialog that posts to `/projects/{id}/environments` and comes back open on that page when refused. **Settings** (`/projects/{id}/settings`, `pages.ProjectSettings`) holds what is the project's and nothing of an environment: its name and description, the link to its shared variables, and its deletion. An environment's page (`pages.EnvironmentShow`) is what runs in it, without the project's tabs. What an environment has of its own is on its Settings (`…/env/{env}/settings`, `pages.EnvironmentSettings`): its name (`db.RenameEnvironment`; the name is a label, everything on a server is named by the id), the link to its shared variables, and its deletion. The environment switcher ends with **All environments**, the way up to the project's page. One place for each thing.
  - Lists of things a person opens are tiles (`ui.Tiles`, `ui.Tile`): projects, and an environment's apps, databases and services together, each kind with its icon (`pages.KindIcon`). All three are added from one page, `…/env/{env}/new` (`pages.ResourceNew`), which leads to the form of the kind chosen. Its groups are Apps, Databases and Services (`kindGroup`). A person's own Compose file, pasted or in a Git repository, is offered under Apps with what else is their own, though what it makes is a service and its form is the service's; Services are the catalogue's templates and nothing else, so its heading can say how many (`data-filter-count`, which `app.js` keeps at what a filter has left). What that page lists is not a tile but an offer (`ui.Offers`, `ui.Offer`): the owner's logo, 48px on a soft square, the name and a line and, under a rule, a foot with Docs and Website at the start (where the catalogue has them: `DBTemplate.Docs` and `Website`, a template's `docs` and `website` header) and the action at the end, which is the card's one link into the dashboard and covers the card. The action says Deploy unless the card leads somewhere else first (`setUp`). The logo is `static/logo-<engine or template key>.svg`, so a new engine or template is its catalogue entry and one file (`TestEveryOfferHasALogo`, for the engines and the templates written for musdash); a name with no file (`static.Logo`) gets its icon in the brand's blue. Every logo there is, is held to the rules by `TestEveryLogoCanBeShown`. A card is at least `--size-offer` high (180px), its foot at the bottom. A service's card names its categories as soft badges (`OfferProps.Tags`, `TagLabels`: bare spans in `.offer-tags`, drawn by the rules of `ui.Badge(text, ui.ToneSoft)` and without a class each, because the page has about a thousand of them), and the Category menu beside the field narrows the page to those chosen, together with the field; Clear filters undoes both. Write the foot's CSS, and any new one, with logical properties (`margin-inline-start`, `border-block-start`), not left and right.
  - A list that has nothing in it says so with `ui.EmptyState` (`ui.EmptyProps`, `docs/plans/empty-states.md`): an icon (its tab's, where it has one), a title that says what is missing, a sentence on what to do about it, the one action as a primary button in its children, and at most one link under that. The default size stands where a page's list would be; `ui.EmptySmall` goes inside a card in place of its table or rows; `ui.EmptyPage` is all a page holds (not found, not allowed). While a list is empty, the button that adds to it is in the state and not also in the page's header or the card's head. A single missing value stays a word in its row ("none", "Never"), and a menu keeps its one line (`ui.MenuNote`). `Plain` makes the title a line of text, for a state under a heading that names it already (a chart's). `TestEmptyListsUseTheComponent` fails for a card whose body is one grey sentence, unless the test names it as a note.
  - Team is one page in three tabs (`pages.TeamTabs`, `docs/plans/team-invitations-tab.md`): Members (`/team`), Invitations (`/team/invitations`, `pages.TeamInvitations`: the links that were sent and not used yet, one table) and Shared variables. An Admin's Invite button and its dialog (`inviteDialog`) are on both of the first two, and whatever `POST /team/invitations` answers is the Invitations tab: the refused form, and the link that is shown once. A member's reset link is shown on Members.
  - Sources (`/sources`, `pages.Sources`) is one table of the team's GitHub Apps and GitLab sources. Its Add source button is a `ui.Menu` of the hosts, each opening the dialog its own process starts from; a host's repository picker answers at `/sources/<host>/{id}/repos` for a source of that kind only. A GitLab token is typed into the dialog and never sent back.
  - Notifications is a page of the sidebar, an Admin's (`/notifications`, `pages.Notifications`): one table of the team's channels. Its Add channel button is a `ui.Menu` of the kinds (`notify.Kinds`), each item opening that kind's dialog; a channel's events and its switch are changed in a dialog of its own. A new kind is a new entry of `notify.Kinds` and its logo, `static/logo-<kind>.svg`, and nothing on the page (`TestEveryChannelKindHasALogo`).
  - A form that makes or changes something with up to five fields is a `ui.FormDialog`, opened by a button with `Opens`, and its page shows what is stored (`ui.KeyValue`), not the fields. The handler that refuses a form renders the same page with the form, and the dialog sets `Open` from it (`data-autoopen`), so the person is where they left off with the errors in place. Several dialogs on a page need field ids of their own, and none may be the id of a section or of the layout (`content`): give the input an `ID` for the page and a `Name` for the form (`ui.TextField` reads the form by the name; a checkbox is `ui.CheckboxNamed`, never a `name` in its attributes, where the second `name` is dropped). `TestSignedInPagesHaveNoInlineScriptOrStyle` fails for an id two elements of a page have: add a new page to its list. Longer forms stay on the page.
  - Whatever stops, removes or replaces something asks first. A submit button gets `ui.Ask(title, question, submit, danger)` and the page's one confirm dialog (`confirmDialog` in the layout) asks; deleting a project, app, database or service is `ui.Confirm`, which wants the name typed. The question says what the action does, so check it against the handler. `TestCriticalFormsAsk` reads the templates and fails for a form at a critical address (`/delete`, `/stop`, `/rollback`, …) that has neither: give it a new such address when one is added.
  - Stored variables are not in a page until asked for. An app's Environment tab, the shared variables pages and a service's Compose tab list names (`pages.Variables`, `ui.Masked`); `…/values` answers "Show values" with the list and its values, and `…/edit` is the editor, a page of its own. Both ask for the role that may change the variables (an Admin for the team's and a server's), and an app's are behind `s.ownSettings`. A Compose form sent with `variables_kept=1` did not hold the variables and leaves them as they are. A webhook secret is fetched the same way (`GET /apps/{id}/webhook-secret`).
  - Keys and tokens of the whole team are one page in two tabs (`handlers_keys.go`, `docs/plans/keys-and-tokens.md`): `/keys` is Private Keys (SSH key pairs), `/keys/tokens` is API Tokens, one table of a person's API tokens and the team's deploy tokens and webhook secrets, with a Type column. Only what exists is a row; a deploy token or a webhook secret is made in a dialog that names the resource (`POST /keys/deploy-tokens`, `/keys/webhook-secrets`), which accepts only an id the dialog offered (`pickedOwner` reads the list the page was drawn from). The per-resource routes are what a row's Replace and Revoke post to. No other page holds a token, a `curl` line or a pointer to this page besides the sidebar, the search (which lists the sidebar's entries) and a form's hint: do not add one.
  - A form whose answer shows what it made cannot answer with a redirect, so a browser's Refresh sends it again. Such a form carries `ui.Once()` and its handler calls `s.sentBefore(w, r, back)` right before it writes: a value seen before changes nothing and leads back with a note. The page it renders sets `ui.Shell.Address`, which `app.js` puts in the address bar so that Refresh is a GET. A new handler that renders a secret after a POST needs all three.
  - Every route is registered in `server.go` with who may call it: `handle("PATTERN", who, h)` where `who` is `open` (no session: assets, and endpoints that prove themselves with a signature or a token), `signedOut`, `member`, `admin` or `owner` (`routes.go`). The session is loaded and CSRF checked for all but `open`; a role too low is refused with a 403 before the handler runs. Do not call `mux.Handle` directly: the tests walk this table (`TestRouteTableRefusesByRole`, `TestTeamOwnedRoutesNeedAnAdmin`). The line between the roles: a Member works with what is in projects; an Admin also changes what the team itself has (servers, sources, Settings, team and server variables, invitations); an Owner also decides roles. A rule a level cannot express (an Admin may remove a Member but not an Admin) is `db.CanManage`, used by the handler and the page alike.
  - `ui.Shell` carries `Admin` and `Owner` so a page leaves out what its reader cannot use. That is for the reader; the route table is what refuses.
  - A handler for a team-owned resource starts with a loader (`loadProject`, `loadApp`) that answers 404 itself when the resource is not the team's.
  - A secret that is shown once (an invitation or reset link, a TOTP key, recovery codes, an API token) is rendered in the response to the POST that made it and nowhere else: not in a redirect, a flash cookie or the log, and not on a later GET, which has only the session to show for itself.
  - Signing in with a second step (`handlers_twostep.go`): the password sets a sealed cookie that names the account for five minutes, and no session exists until the code is right. Attempts at an account's password and second step are counted per account, in `s.accounts`: a limiter of their own, because the by-address one (`s.logins`) can be filled from many addresses and a full table is emptied. Turning the second step on or off, and making an API token, ask for the password again.
  - Home (`GET /{$}`, `handlers_home.go`, queries in `db/home.go`) is the page a person lands on: what was done lately (`db.RecentEvents`: every deployment, but of each database and each task only the latest backup or run, or a task that runs every minute would be all it holds), the projects last deployed in, and the servers. It reads the database only and never asks a server: what a server uses is its last stored sample, and one older than five minutes is not shown as the present. Every list has a limit. It asks for itself again (`/home/live`) only while something is in progress. The Projects list is at `/projects`.
  - Apps, databases and services share one name namespace per environment (`db.nameTaken`): the name is the resource's address on the environment's Docker network. A service that joined that network also holds the names of its Compose services there.
  - A service's endpoint is what a domain points at: `domains` rows with `resource_kind = 'service'` carry an endpoint id, not a service id.
  - Tables shared across resource kinds (`domains`, `env_vars`, `storages`) are keyed by `(resource_kind, resource_id)`; their queries do not check the team, so only call them with a resource a loader returned.
  - Routes that change what an app is configured with are wrapped in `s.ownSettings`, which turns a preview away: add it to any new one.
  - `api.go` is `/api/v1`: it reads what the pages show and does what their buttons do. A request carries a person's API token (`msd_…`, stored as SHA-256) and nothing else: the session cookie is never read there, which is what keeps another site from calling the API through a signed-in browser, and no page accepts a token. Answers are built field by field from the `api*` structs; never marshal a `db` row, which holds sealed values and hashes (`TestAPINeverReturnsSecrets` reads every GET route with a token that only reads and must be given each new one). Every route so far is something a Member may do; a route for more must check `token.Role`. A token has a set of permissions (`db.NormalAbilities`: `read`, `write`, `deploy`, `read:sensitive`, or `root` alone), each route names the one it asks for (`s.api(needs, h)`), and none implies another except that `root` is all and `read:sensitive` reads. They narrow what the person may do and never add to it. `read:sensitive` is what an answer checks before it holds a value (`apiAppEnvs`, the password in `apiDatabase`); `TestAPITokenPermissions` wants an example of every new route.
  - `handlers_webhooks.go` holds the three endpoints other machines call (`/webhooks/github/{id}`, `/webhooks/git/{id}`, `/api/v1/deploy`). They have no session or CSRF; each authenticates by signature or bearer token and is rate-limited by address. Unknown id, missing secret and bad signature must stay indistinguishable.
  - A terminal is the one WebSocket (`ws.go`, written out here: handshake, masked frames in, messages of at most 64 KB) and the one place where what a person types is run. `handlers_terminal.go` keeps it narrow: a fixed `docker exec` in a container whose name comes from the database (for a service, from the server's own list of that service's containers), a request from the dashboard's own origin, the session's form token in the first message, eight at once. Whichever side ends hangs up the other from its own goroutine (`end`): the goroutine typing into a shell that does not read cannot notice anything. Docker ends only its own client when a terminal goes away, so the handler then ends what the terminal ran itself (`hangUp`: the shell carries a mark in its environment, and the session of what carries it and still has the terminal is sent SIGHUP, so a second terminal in the container and what left the terminal with `setsid` are not touched), before the terminal's place is given back; shutting down waits for that (`WaitTerminals`). `static/terminal.js` is the emulator; assets are read into memory when first asked for, so it costs nothing until a terminal page is opened.
  - Charts are SVG written by the server (`ui/chart.go`), one series each, no script. Usage fragments poll while a page is open and stop after `maxPolls`.
  - Live logs are Server-Sent Events (`sse.go`): output is HTML-escaped, streams are capped at 16, and the producing process dies with the request context.

## UI design system

Colours are in `internal/web/assets/colors.css` in two layers: `--palette-*` holds the raw hex values (Primer's light theme, MIT, under our own names; the only place a hex is written) and `--color-*` holds the roles components use. Re-skin by repointing a role, never by writing a hex elsewhere. Everything else is in `input.css` and the "Design system" section of the phase 0 plan (its colour table predates `colors.css`):

- Light mode only, blue brand, no web fonts, no icon font (icons are inline SVG via `ui.Icon`).
- Tailwind's default palette, type scale, weights, radii and shadows are disabled (`--color-*: initial` etc.) and replaced with project tokens in `@theme`. Only token names exist as utilities (`brand-600`, `ink`, `ink-soft`, `ink-mute`, `ink-faint`, `canvas`, `paper`, `sunk`, `veil`, `line`, `info`/`ok`/`warn`/`danger`/`idle` and their `-soft` tints and `-line` borders). Never write a raw colour, size or radius.
- The look follows GitHub Primer's light theme, written as our own tokens and classes; nothing of Primer's is imported. Page and cards are both white and told apart by a border; `sunk` grey is the frame (sidebar, card head and foot, a resting button). Hover on something with no fill of its own uses `veil`, so it works on either. Controls are 32px (28px small), text is 14px, labels are semibold, and there is no bold and no uppercase label.
- Controls use component classes from `@layer components` (`.btn .btn-primary`, `.field`, `.input`, `.card`, …) so markup carries one class per control, not a utility pile. Extend these and the `ui` components rather than styling per page.
- A product's mark in its owner's colours is `ui.Logo(name)`: an `<img>` of the file `static/logo-<name>.svg` (or `.webp`, see `static.Logo`), the size of an icon (`MenuItemProps.Logo` puts one in a menu). Its hex values are the image's own and stay in the file, as the favicon's do. The file is drawn with attributes only (`fill="…"`, never `style="…"`, which the CSP sent with the image drops) and reaches for no other address. Where a logo comes from is in `static/logos.LICENSE`. A name that comes from data is asked of `static.Has` first.
- Machine facts (domains, image tags, ports, hashes, logs) use the mono stack. State is always written as text as well as colour.
- A state in a pill has an icon as well: the tone's, turning (`animate-spin`) while something is in progress. Waiting in the queue is not in progress: it has the info tone's soft blue (`ui.ToneInfo`) and a clock that does not turn. A pill is always `ui.Pill` (a tone), `ui.StatePill` or `ui.StatusPill` (a state) or `ui.JobPill` (a deployment, backup or run, whose "running" means in progress), never a `<span class="pill">` of a page's own, which would have no icon. Badges have none; `ui.ToneSoft` is a badge's alone, a pale blue outline for a label that sorts a thing and says nothing of its state.
- Tailwind scans only `internal/web/ui`, `internal/web/pages` and `static/app.js` (`source(none)` plus explicit `@source` lines); classes used elsewhere will not be generated.

## Workflow conventions

- Each plan task ends with `go vet ./... && go test ./...` green, a self-review of the diff, and a commit to `main` (remote `origin`). Commit subjects follow `Phase N task M: …`.
- New behaviour gets tests alongside it, written first where the plan says so. Tests use real SQLite files in `t.TempDir()` and real processes, not mocks.
- Comments in this codebase explain why (the constraint or failure being avoided), not what; match that.

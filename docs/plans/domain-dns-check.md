# A domain of one's own, and a check of its DNS

Asked for on 2026-10-08, after the Add domain dialog: "support a real domain: if I buy asd.com, musdash should support that", and "a button to check DNS for a domain". Planned, the plan reviewed, built and the code reviewed, in that order.

**What was there.** A bought domain already works: entered in the dialog with https, the proxy serves it, and the first request over HTTPS has a certificate ordered from Let's Encrypt, once the domain's DNS leads to the server. `asd.com` is as good a name as `app.asd.com`, and the www box routes the other form as a redirect. What a person who has just bought a domain does not get is the one thing they have to do themselves: the page says "point the domain's DNS at the app's server" and neither names the record nor says whether it is there. A domain whose DNS is wrong is a row like any other, and the only sign is a browser error some minutes later.

| # | Decision | Why |
|---|---|---|
| 1 | The dialog and the tab's head name the record: "an A record for the domain with the value 203.0.113.7" (AAAA for an IPv6 address), from the app's server's public IP address. Without one stored they say what they said, and where the address is set | It is the step that is the person's own, and the value is one musdash has |
| 2 | Each domain that is not a generated address has **Check DNS** in its row. `GET …/app/{id}/domains/{did}/dns` (a Member's, placed, behind `ownSettings` like the tab) answers a fragment that htmx puts under the domain's name | A check reads and changes nothing, so it is a GET. A generated address needs no DNS |
| 3 | The name that is looked up is the stored row's, found among the app's own domains by its id. Nothing typed reaches the resolver | A lookup of whatever a request names would be a way to make the server ask about any name |
| 4 | It is asked of the control plane's own resolver (`net.Resolver.LookupNetIP`), five seconds at most for the whole check; `Server.Resolve` replaces it in tests | No dependency, no connection to the name itself. Tests do not reach the internet |
| 5 | With the www box ticked the other form of the name is checked as well, a line each | The redirect is a host of its own with a certificate of its own; it is the one people forget |
| 6 | The verdict is one function over the answer and the server's address (`dnsVerdict`), in six cases: every address is the server's (ok); none is, or only some are (warning, with the addresses and the record to change); the name has no address (warning, with the record to add and that a new one takes a while to be seen); the lookup failed (neutral, try again); the server has no public address stored, so nothing can be compared (neutral, the addresses and where to set it) | Each is something a person can act on. State is a pill with an icon and words, never colour alone |
| 7 | An answer is the outside's word: only what parses as an address is shown, at most four of them | A name can have any number of records |
| 8 | Nothing is stored and nothing is remembered between checks | DNS changes under us, and the RAM rules keep no caches |
| 9 | Adding a domain does not wait for a lookup and is not refused over one | The record is often made after the domain is added. The check is there when the person wants it |
| 10 | Where a CDN is in front of a domain, its address is not the server's. The warning says that this is so and may be meant | Otherwise the check would call a working set-up broken |

**Not in this piece:** a service's endpoints and the dashboard's own domain have the same need; they can take `dnsVerdict` as it is. The certificate's own state (ordered, refused, why) is the proxy's and is not shown here.

**Review of the plan.** Two things changed. The www form was computed inline in `BuildRoutes`; the check needs the same rule, so it becomes one function both use (`deploy.OtherForm`), or the two would drift. And the fragment answers 200 with a line of its own when the check cannot be made at all (the server row is gone), as a switcher does, because htmx swaps nothing else in; an id that is not one of the app's domains is still 404, since no page of ours links to it.

**Tests:** the verdict in each of its cases, with an IPv6 server, the same address twice, and more addresses than are shown; the tab names the record in its head and in the dialog; a domain of one's own has the button and a generated address has none; the check of a domain with its www form answers a line for each and is a fragment, not a page; only the stored names are looked up; another app's domain and an unknown id are not found and nothing is looked up for them.

**Review of the code.** Looked at in a browser against the real resolver, with three domains: one that leads to the server and elsewhere, one that leads elsewhere, one that does not exist. Three things changed. The answer was under the domain's name in the first cell, which made that column wide and stacked the badges of the next: it is a row of its own under the domain's, over the whole width (`.table-under`), empty until asked, and what is in it does not decide how wide the columns are. A name with an A record for the server and an AAAA record besides was told that requests to the other "do not reach the app", which is wrong when that is the server's own IPv6 address, of which musdash stores none: the line now says that only the one address is known to be the server's, and what follows if the others are not. And the page said "Point each domain's DNS at the app's server" in two places; both name the record.

## 1. The project in the header is a switcher

**Asked:** the project step of the trail lets a person go to another project, as the team's and the environment's steps do.

**What was there:** `Default team ⌄ / Projects / Shop / production ⌄ / web ⌄`. The project step was a link: to the environment's page from inside an environment, to the project's first environment from its Settings.

| # | Decision | Why |
|---|---|---|
| 1 | The step is a `Crumb` with a `Menu`, built by one helper, `projectCrumb`, that `projectCrumbs` and `envCrumbs` both use | Every page under a project gets it, and none can differ |
| 2 | `GET /switch/projects?at=<id>` (member) answers the team's projects, each a link to `/projects/{id}`, the one named by `at` marked; then a rule and **All projects** to `/projects` | The team's switcher has no id in its path either: the session says whose projects. `at` is only compared, never written back |
| 3 | It has a filter field ("Find a project") | A team can have many projects; the resource switcher has one for the same reason |
| 4 | The list is `db.ListProjects`, the query the Projects page runs | No second query to keep in step. Its counts are four indexed sub-selects a project, and it runs only when a menu is opened |
| 5 | The "Projects" step before it stays | It is the way to the list in one click, and the trail still reads as a path |
| 6 | The way back from a resource to its environment's page is the environment switcher's marked option | The project step led there; a button that opens a menu cannot also be a link |

**Review of the plan.** `projectCrumbs` had a branch for a trail that ends at the project, which no handler asks for: it goes, so the helper has one shape. Nothing else changed.

**Tests:** the switcher lists the team's projects and marks the current one, leaves another team's out, and leads to the list; the project step of an environment's page, an app's and the project's Settings is the switcher.

**Review of the code.** Read the diff and opened the menu in a browser on an app's page: three projects, the current one marked, the filter narrows, All projects leads to the list. Nothing to change.

## 4. Sources: GitLab beside GitHub

**Asked:** the Sources page supports GitLab too. A button at the end of its header opens a menu, GitHub or GitLab, and the choice continues that host's own process.

**What was there:** one card, "GitHub Apps". A source was a GitHub App and nothing else: the table's `kind` allowed no other value, a row counted as connected when it had an App id, and five places took a source id to mean GitHub (the clone, the Git form's host check, the repository picker, the pull request comment, and the Keys page's "a GitHub App reports the pushes").

**What a GitLab source is.** GitLab has nothing like GitHub's App manifest, where a click creates the integration. What it has is an access token (a person's, a group's or a project's). So a GitLab source is: a name, the instance's address (`https://gitlab.com` unless self-hosted) and a token with `read_api` and `read_repository`, sealed. With it musdash lists the repositories the token can read in the Git form's picker, and clones private ones over HTTPS.

| # | Decision | Why |
|---|---|---|
| 1 | Migration 0017 rebuilds `git_sources`: `kind` may be `gitlab`, and there are `base_url` and `token` (sealed) columns | The `CHECK` on `kind` cannot be altered in place. A token in `private_key` would be a column that lies about what it holds |
| 2 | "Not finished" is said of GitHub rows only: `ListGitSources`, `PendingGitSource`, `DeleteStaleGitSources`, `GitSource.Ready` and Home's count of sources ask for the kind as well as the App id | A GitLab row has no App id and is whole from the start. Left as they were, the daily clean-up would have deleted every GitLab source as a manifest flow nobody finished |
| 3 | `source.GitLab` asks two things: whose token this is (`/api/v4/user`), when the source is made, and which projects it reads (`/api/v4/projects?membership=true&simple=true`, up to the picker's 300) | The first refuses a wrong token while the person is still in the dialog. No more of the API is needed, so no more of it is written |
| 4 | Its HTTP client connects only where `netguard.Policy` allows, sends the token as `Authorization: Bearer`, and follows no redirect | The address is typed by an Admin and musdash connects to it: it must not be a way to the server's own services (CLAUDE.md, `notify.Dialer`). A redirect would carry the token to wherever the instance pointed |
| 5 | The address must be `https://host[:port]`, nothing after it | A token over plain HTTP is a token on the wire. A GitLab under a path of a host is rare and can come when somebody has one |
| 6 | What GitLab answers is data: a user name and a project path are checked against a strict pattern before they are kept or become part of an address, and a branch name is cut to size | The same rule as for a remote server's answers (CLAUDE.md) |
| 7 | The clone authenticates as the GitHub one does: an `http.<base>.extraHeader` in git's environment, scoped to the instance, with the token as the password of `oauth2`. The repository must be on the source's own host, checked when the form is saved and again when the clone is made | The token is GitLab's and goes to that GitLab and nowhere else, whatever address the app was saved with |
| 8 | Pushes are not reported by the source. A push deploys through the app's own webhook, with a secret from Keys & tokens, which already reads GitLab's push and merge request events | Registering a webhook on the project for the person would need a token with the `api` scope: the right to change everything the person can. Reading is all this asks for. So the Keys page's "a GitHub App reports the pushes" is said of GitHub Apps only (`ViaApp`), and an app through a GitLab source is offered a webhook secret |
| 9 | A preview is not announced on a merge request | The comment is written through the GitHub App. `announce` returns for any other kind |
| 10 | The page is one table of the sources: Name, Type, Account, and what can be done. The header's **Add source** is a `ui.Menu` with GitHub and GitLab, each opening its dialog; with no source it is in the empty state | Asked for, and the shape Notifications has since 3 |
| 11 | Routes: `POST /sources/gitlab` (admin), `GET /sources/gitlab/{id}/repos` (member), `POST /sources/gitlab/{id}/delete` (admin). Removing is one handler for both kinds; each kind's repository list answers only for its own kind | `TestTeamOwnedRoutesNeedAnAdmin` covers `/sources` already |
| 12 | The Git form names the source's kind ("GitLab: work"), its picker asks the kind's own list, and Add resource has a tile for a private repository through a GitLab token | Otherwise a GitLab source would be offered as a GitHub App |
| 13 | The icon is Hugeicons' Gitlab, from the set the others are from | One set, one licence |
| 14 | The token is typed into a dialog and never comes back: not in a refused form, not on the page | CLAUDE.md, a secret shown once. Here it is not even shown once: the person brought it |

**Review of the plan.** Three things changed. The first draft kept the token in `private_key` to save a migration, but the `CHECK` on `kind` needs one anyway, so the columns are honest (1). It also missed that the clean-up job deletes rows without an App id (2): found by reading every query on the table, not only the ones the feature calls. And a GitLab source would have been listed on the Keys page as reporting its own pushes, so that nobody could make the webhook secret that 8 depends on.

**Not done, and said so on the page:** a push deploys only once the project has the webhook; there is no comment on a merge request.

**Tests:** `source`: the token's owner, a refused token, a redirect that is not followed, the project list with a name that is not a path left out, the address rules. `db`: a GitLab source is listed, counted, never pending and not cleaned up. `deploy`: the clone's address and header, and a repository on another host refused. `web`: the menu and its two dialogs; making a source with a good and a bad token, the token nowhere on the page; the picker; the Git form accepting the source's host and refusing another; the Keys page offering a webhook secret; removing one in use refused.

**Review of the code.** Read the whole diff with the five places a source id meant GitHub in hand: each asks the row's kind now, and `sourceHost` is the one place that says which host a source reads. Two things came out of it. The repository list of one kind answered for a source of the other (a GitLab id at GitHub's address would have been asked for an App key it does not have): `loadRepoSource` answers 404 for the wrong kind, and the test asks. And the README said how GitHub and deploy keys read a private repository and nothing of GitLab, nor that a GitLab source needs the webhook: both are there.

Checked in a browser: the table with one source of each kind, the menu at the end of the header, the Connect GitLab dialog, and a made-up token sent to the real gitlab.com, which answered 401 and came back as "GitLab did not accept the token" in the open dialog with the token field empty. An existing GitHub App's row came through migration 0017 on a database that had one.

**Still to be checked on the VPS** (it needs a real token and a private repository): the clone of a private GitLab repository, the picker against a real account, and a push through the app's webhook.

**Found when pushing.** GitHub refused the push: a made-up token in the new web test was `glpat-` and exactly twenty characters, which is how GitLab writes a real one, and push protection took it for a leak. The test's values are written in another shape now, and say why.

## 6. Notification channels have their logos, in colour

Asked for after the five above: "use colored icons for notifications Channels", from selfh.st's collection or anywhere else.

| # | Decision | Why |
|---|---|---|
| 1 | A logo is a file, `internal/web/static/logo-<name>.svg`, drawn by `ui.Logo(name)` as an `<img>` of 16px | `ui.Icon` is one colour, the text's, and a logo is its owner's colours. As a file it is fetched once and cached for good, where seven logos written into the page would be sent with every Notifications page |
| 2 | Discord, Slack, Mattermost, Telegram and Pushover are selfh.st's (`selfhst/icons`, CC BY 4.0), with every `style="fill:…"` rewritten as the attribute it stands for and nothing else changed | The page's CSP (`style-src 'self'`) is sent with the image as well, and a browser that reads it there drops a `style` attribute: the logo would be black. An attribute is not a style to the CSP |
| 3 | Email and Webhook are drawn here: an envelope in the brand's blue, the webhook mark of the icon set in the palette's purple | The collection has neither, since neither is a product. They are files like the others, so the page asks one question of a kind and not two |
| 4 | The hex values stay in the files | `colors.css` holds the design system's colours. A logo's are its owner's and an image's own, as the favicon's are |
| 5 | The file is named by the channel's kind, so `notify.Kinds` stays the one list. A kind without a file fails a test, not a page: `channelLogo` draws the bell for a kind it does not know | A new kind is still one entry and one file. A row of a kind that was removed later must not take the page down (`static.URL` panics for a name it does not have) |
| 6 | `ui.MenuItemProps` gets `Logo`, beside `Icon` | The menu of kinds is where a logo says most: seven names told apart before they are read |
| 7 | In the table the logo leads the row, before the name, and Type stays a badge | What the Sources table does with its icon; the two pages are one shape |
| 8 | The dialogs keep their titles as text | `ui.FormDialog` takes a title as a string, and the person has just chosen the kind from its logo |
| 9 | The credit is in the README beside Hugeicons', and in `internal/web/static/logos.LICENSE` | CC BY asks for the source, the licence and that changes are said. The marks are their owners' trademarks either way |

**Review of the plan.** Two things changed. The first draft was one sprite file with a `<use href>` from the page: one request for seven. Telegram's logo has a gradient, and a gradient inside a sprite that another document uses is what Safari has drawn wrongly before, which cannot be checked from here; seven small files that are cached for good cost nothing worth that. And the files were to be the collection's own, byte for byte, until reading one showed its colours are in `style` attributes (2).

**Tests:** every kind of `notify.Kinds` has its file, served as `image/svg+xml`, with no `style`, no script and no address in it; the Notifications page has a logo for every item of the menu and one in a channel's row.

**Review of the code.** Read the diff against the plan's nine rows. Three things came out of it. `ui.Logo` panics for a name without a file, which is right for a name written in a template and wrong for one read from a row, so `static.Has` exists and `channelLogo` asks it (5); the test renders a row of a kind nobody has. The menu's rule that sets an icon two pixels down to meet its label named `.icon` only, so a logo sat high: it names `.logo` too, in both places. And the webhook mark was three open curves until its joints were drawn, which at 16 pixels is what makes it the mark and not a knot.

The component gallery has a Logos row, since the component is the design system's now. `make rss` is unchanged: a logo is read when a page that shows it is first drawn, not when the server starts.

Checked in a browser: the menu with its seven logos, the table with an Email and a Telegram channel, every image loaded (none black, so no colour was lost to the CSP) and nothing new in the console. Not checked: Safari, which this machine's preview is not.

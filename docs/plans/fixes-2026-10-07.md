# Fixes of 2026-10-07

Five things asked for on 2026-10-07. Each was planned, the plan reviewed, built, and the code reviewed, in that order; what the reviews changed is said under each.

## 1. The project in the header is a switcher

**Asked:** the project step of the trail lets a person go to another project, as the team's and the environment's steps do.

**What was there:** `Default team ⌄ / Projects / Shop / production ⌄ / web ⌄`. The project step was a link: to the environment's page from inside an environment, to the project's first environment from its Settings.

| # | Decision | Why |
|---|---|---|
| 1 | The step is a `Crumb` with a `Menu`, built by one helper, `projectCrumb`, that `projectCrumbs` and `envCrumbs` both use | Every page under a project gets it, and none can differ |
| 2 | `GET /switch/projects?at=<id>` (member) answers the team's projects, each a link to `/projects/{id}`, the one named by `at` marked; then a rule and **All projects** to `/projects` | The team's switcher has no id in its path either: the session says whose projects. `at` is only compared, never written back |
| 3 | It has a filter field ("Find a project") | A team can have many projects; the resource switcher has one for the same reason |
| 4 | The list is `db.ListProjects`, the query the Projects page runs | No second query to keep in step. Its counts are four indexed sub-selects a project, and it runs only when a menu is opened |
| 5 | The "Projects" step before it stays | It is the way to the list in one click, and the trail still reads as a path |
| 6 | The way back from a resource to its environment's page is the environment switcher's marked option | The project step led there; a button that opens a menu cannot also be a link |

**Review of the plan.** `projectCrumbs` had a branch for a trail that ends at the project, which no handler asks for: it goes, so the helper has one shape. Nothing else changed.

**Tests:** the switcher lists the team's projects and marks the current one, leaves another team's out, and leads to the list; the project step of an environment's page, an app's and the project's Settings is the switcher.

**Review of the code.** Read the diff and opened the menu in a browser on an app's page: three projects, the current one marked, the filter narrows, All projects leads to the list. Nothing to change.

## 2. Domains is an app's tab, and only an app's

**Asked:** the Domains tab belongs to an app, not to a project, a database or a service, and shows that app's domains.

**What was there:** a project had a Domains tab listing every address of what it runs (apps' domains and services' endpoints, in every environment) with a dialog that added a domain to an app chosen from a list. An app's own domains were a card at the bottom of its Settings.

| # | Decision | Why |
|---|---|---|
| 1 | The project's tab goes whole: `GET` and `POST /projects/{id}/domains`, their handlers, `pages.ProjectDomains`, `db.ProjectDomains` and the `from=project` way back in `appDomainDelete` | Asked for. A route that only fed the tab is dead once the tab is gone |
| 2 | An app has a Domains tab, `GET /apps/{id}/domains`, between Environment and Storage. It holds what the Settings card held: the list as a table, and the Add domain dialog | "It shows the domains for this app." Settings was the longest page an app has; this takes its last card but one off it |
| 3 | The route is wrapped in `s.ownSettings`, and a preview has no such tab | A preview's address is given to it, not chosen (CLAUDE.md). Its Overview still shows the address |
| 4 | `POST /apps/{id}/domains` and `…/{did}/delete` keep their addresses and answer to the tab; a refused form comes back on the tab with the dialog open | Nothing that posts there has to change but where it reads the form from |
| 5 | Overview's Domains card leads to the tab ("Manage", "Add domain") | It led to `/settings#domains` |
| 6 | A service's endpoints stay in its Settings, a database's public port in its own | They are not domains a person adds to a list; nothing was asked of them but that they have no tab |
| 7 | `test/vps`: `lib._compat` sends a script that looks for the form on Settings to the tab, and the scripts that read the Remove forms read the tab | The suites are run against a VPS later and must find the form |

**Review of the plan.** Two things were missing. The flash after an app is made with a taken domain said "under Settings": it names the tab now. And `TestSignedInPagesHaveNoInlineScriptOrStyle` walks a list of pages that named the project's tab: the app's takes its place, so the id check covers the moved dialog.

**Tests:** the tab lists the app's domains and no other app's, adds and removes and comes back to itself; a refused form answers 422 with the dialog open; a preview is turned away; the project has no Domains tab and its old address is not found; Settings no longer holds the form.

**Review of the code.** The README still sent a reader to "Settings → Domains" and to a project's Domains tab: both lines name the app's tab now. Nine `test/vps` scripts read the form or the Remove buttons from Settings; they read the tab. Checked in a browser: the tab between Environment and Storage, the table, and the dialog.

## 3. Notifications is a page of its own, in the sidebar

**Asked:** Notifications leaves the Settings tabs and is an entry of the sidebar. The page is a table of the channels. A button at the end of its header opens a menu of every kind of channel; choosing one (Telegram, say) opens that kind's dialog, and the channel it makes is a row of the table. The empty state has the same button.

**What was there:** `/settings/notifications`, a tab of Settings. Each channel was a block with its event checkboxes written out and a Save button; under them, a second card held one button a kind.

| # | Decision | Why |
|---|---|---|
| 1 | The page is `/notifications`, with `POST /notifications`, `/notifications/{cid}`, `…/test` and `…/delete`. The old addresses go | A page of the sidebar is not under `/settings`. Nothing outside links to the old ones but the test message's own link, which moves |
| 2 | It stays an Admin's, and the sidebar entry is an Admin's (`NavItem.Admin`), in Administration between Keys & tokens and Settings | Channels are the team's own (CLAUDE.md: an Admin changes what the team itself has). `TestTeamOwnedRoutesNeedAnAdmin` learns the new prefix |
| 3 | The table: Name, Type, Tells about, State, and what can be done: Send a test, Edit, Remove | One row a channel, as asked |
| 4 | "Tells about" is short words (Deployments, Backups, Tasks, Containers, Disk), "Everything" for all and "Nothing" for none. `notify.Events` gets a `Short` beside its `Label` | The sentences the checkboxes carry are too long for a cell, five times over |
| 5 | A channel's events and its on/off switch are edited in a dialog, one a channel (`edit-channel-<id>`), holding the checkboxes the block held. The field names keep the channel's id, so no two dialogs share an id | A table row cannot hold six checkboxes. What is stored is shown; the form is in a dialog (CLAUDE.md) |
| 6 | The button is a `ui.Menu` whose button is the primary one, "Add channel". Its items are the kinds; each opens the kind's dialog. `ui.MenuItem` gets `Opens` for that: a button that opens a dialog and sends no form | The menu component exists and is steered by the keyboard already. An item so far was a link or a submit button |
| 7 | `app.js`: a `data-open` button inside a menu gives the focus to the menu's own button before the dialog opens | A dialog hands the focus back to what had it, and an item of a menu that has shut is not there to take it. The confirm dialog does the same |
| 8 | While there is no channel the button is in the empty state and not in the header | CLAUDE.md's rule for a list that is empty |
| 9 | The kinds have no icon in the menu | The set has a bell and a webhook and nothing for the other five; two icons in seven lines would look like a mistake |
| 10 | `test/vps`: the scripts name the new addresses | They are run against a VPS later |

**Review of the plan.** The menu's id would have been `add-channel`, and its list `add-channel-list`: beside dialogs called `add-channel-<kind>` that is one new kind named "list" away from an id used twice. The menu is `new-channel`. And the Edit dialog must say what it cannot do: a channel's address and tokens are not shown again, so they are not edited either, and the dialog says to remove the channel and add it again.

**Tests:** the page answers at `/notifications` and the old address is not found; the menu lists every kind and each item opens its dialog; an empty page has the menu in its empty state and none in the header, a page with a channel the other way round; a channel is a row with its type, what it is told and its state, and an Edit dialog of its own; the sidebar has the entry for an Admin and not for a Member, and Settings no longer has the tab.

**Review of the code.** The README still said "Settings, Notifications" in two places; both name the page now. CLAUDE.md says what the page is and that a `MenuItem` can open a dialog. Checked in a browser: the empty state with its menu, the menu at the end of the header once there are channels (hung from the button's right edge), Telegram's dialog opening from the menu, the table, and a channel's Edit dialog.

## 5. Tags: no Deploy all, and a switcher in the header

(Built before 4, which is the long one.)

**Asked:** the tag's page loses Deploy all, and the tag's step of the header is a switcher to the team's other tags.

**What was there:** a tag's page had Rename, Delete and, when anything had the tag, Deploy all, which queued a deployment of everything tagged. Its trail was `Tags / nightly`, the last step plain text.

| # | Decision | Why |
|---|---|---|
| 1 | The button goes, with `POST /tags/{tag}/deploy` and its handler | Asked for. A route no page posts to is one more thing to guard for nothing |
| 2 | `deploy.DeployTag` goes too, with its tests | The web route was its only caller: the API's `POST /api/v1/deploy?tag=` gathers what is tagged itself and queues it through `queueApp` and `queueService`, which its own tests cover. Deploying by tag stays possible, from a pipeline |
| 3 | The words that promised a button change: a tag groups what belongs together, its page lists them, and the API deploys them in one call | The Tags page, the New tag dialog and the tags card of an app's and a service's Settings all said "deployed together, from the Tags page" |
| 4 | The tag's step is a switcher: `GET /switch/tags?at=<tag>` (member) lists the team's tags (`db.ListTags`), each a link to its page, the current one marked; then a rule and **All tags** | As the project's step in 1 |
| 5 | It has a filter field | A team has up to `MaxTeamTags` tags |
| 6 | Each option says how many things have the tag | It is what the Tags page's tiles say, and tells an empty tag from a used one before going there |

**Review of the plan.** The tag's page test asserts that the page names no API address and no token (CLAUDE.md: nothing but the Keys page holds those). The new words say "the API" and nothing more, so that still holds. `test/vps` has three scripts that press Deploy all: they deploy the tag through the API with the deploy token instead, which is what a person does now.

**Tests:** the tag's page has no Deploy all and its old address is not found; the tag step is a switcher; the switcher lists the team's tags and marks the current one, and another team's tag is not in it.

**Review of the code.** A later step of the tags test renamed a tag to the name of one that the removed "deploy an empty tag" step had made: the test makes that tag itself now, and asks the switcher to call it empty. Checked in a browser: the tag's page with Rename and Delete only, and the switcher with three tags, their counts, and All tags.
